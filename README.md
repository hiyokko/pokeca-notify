# ポケカ通知

毎日09:00（日本時間）に、**ポケモンセンターオンラインとAmazon.co.jp販売分**のBOX・BOX入りセットについて、**新しい抽選開始と再販・在庫復活**をDiscordへ通知するGitHub Actionsです。記事の更新自体は通知しません。別枠で**トレトクのポケモンPSAオリパ・PSA10くじの新規販売告知**も通知します。

## 対象と情報源

既存・新規の拡張パックBOX、ルリナセット・イーブイズセットなどBOXを含むセットを発見対象にします。バラパック、BOXを含まないセット、デッキ、オリパ、サプライ、他店の販売を除外します（下記のトレトクPSAオリパは例外として別処理）。商品仕様から判断できない商品は通知しません。

| 情報源 | 用途 |
| --- | --- |
| [ポケゲトちゃんねる](https://pokemon-infomation.com/) | 再販・抽選カテゴリ全記事から商品仕様と対象2店舗の受付期間を抽出。古い記事の変更も確認 |
| [ポケカ抽選ボード](https://chusen-board.com/) | Amazon招待受付中一覧と商品URL。別ソースでポケカBOXと確認した商品のみ採用 |
| [Mirar](https://otoku-mirar.com/amazon-pokemon-card-request-sell) | ポケカBOXのAmazon招待受付中・終了一覧 |
| [カード抽選まとめ](https://cardchusen.com/) | ポケカかつ対象店舗の商品URLを発見。掲載だけでは抽選開始と判定しない |
| Amazon商品ページ | 販売元Amazon.co.jp・購入ボタン・在庫表示が確認できた場合の在庫判定 |

## 通知ルール

- 抽選: 明確な受付期間が開始したとき、終了後に次の抽選回が始まったとき、または既存の複数ソースで新たに受付中と確認できたとき。
- 再販: 明示された再販期間の開始、または確認済みの販売不可→購入可能への変化。
- 期限切れ・受付開始前・記事の日時更新・価格修正・期限延長・当選発表・当選者の購入期間は通知しません。
- 受付開始前の期間を保存し、記事が変わらなくても受付開始時刻を過ぎた日次実行で判定します。
- 商品名・店舗・販売種別で統合。同じ購入機会が複数サイトに載っても1件にまとめます。
- 初回と新ソース追加時は既存情報を基準として保存し、過去の抽選を一斉送信しません。
- 不明や取得失敗を「在庫なし／受付終了」に変換しません。変化がない日は商品通知①を送りません。日次ヘルスチェック②は送ります。
- 情報サイトを根拠にした通知は情報元を明記します。公式確認済みとは表示しません。

## トレトクのPSAオリパ通知

[公式ブログのお知らせ](https://www.toretoku.jp/blog/category/notice/)を公開APIから毎日取得します。記事の更新日時だけでなく、本文の商品名と販売日・販売内容を読み取ります。BOX条件とは独立して `check_toretoku_psa_oripa` で切り替えられます。

- ポケモンのPSAオリパ／PSA10くじの新しい販売回・追加販売が対象。通常オリパ、他カードゲーム、PSAの解説や注意事項だけの言及は除外します。
- 販売予定が発表された時点で通知します。未来の日付は初回導入時も通知対象で、過去の販売回は履歴だけ保存します。予定日の当日に再通知はしません。
- 販売日、取得できた価格・販売数・購入制限、公式告知リンクを送ります。在庫の有無は確認しません。
- 同じ販売日の告知は記事をまたいで1件に統合。表・詳細欄の二重掲載や価格修正では再通知しません。同日に複数種類ある場合も1件にまとめます。
- 日付未定の場合は、監視開始後に公開された、公開から7日以内の新着記事で商品名・販売の明示・価格が確認できた告知のみ対象にします。後から同じ記事に日付が付いても再通知しません。
- 年省略時は記事の公開年を使用（12月記事の1月は翌年）。更新年へ自動的に読み替えません。
- お知らせカテゴリ以外の記事、画像だけの日付、未知の商品名表記・HTML構造は取りこぼす場合があります。取得エラーは日次処理の失敗としてwatchdogの自動再試行対象になります。

## 情報源の障害への対応

公開情報源のGETだけ、HTTP 408/429/500/502/503/504や接続タイムアウトを最大4回まで試します。通常の待機は2・5・15秒に小さなばらつきを加え、実行全体の再試行待機は90秒以内です。403/404、証明書検証エラー、解析エラーはこの再試行の対象にしません。Discord送信やGitHubへの書込みをこの処理で再試行しません。

`Retry-After`（秒数またはHTTP日時）を尊重します。30秒を超える指定はランナーで待たず、ホストごとの再取得可能時刻を`monitor-state`へ保存します。同じ実行中の別APIや次の実行もその時刻までアクセスしません。短い再試行を使い切ったホストも5分間は追加アクセスを止めます。

watchdogは失敗した実行・試行番号に対応する再取得可能時刻を読み、時刻が来るまで自動rerunの回数を消費せず待ちます。その後、30分以上の間隔と最大2回の制限内で再実行します。情報源が引き続き停止している場合は、復旧したとは通知しません。

各情報源で発見したAmazon商品URLを商品台帳へ保存します。情報源の取得失敗や一覧からの掲載消失があっても、保存済みのBOX情報・商品台帳にあるURLは直接の在庫確認対象として維持します。保存済みの古い抽選受付状況・在庫状況は今回の取得成功や新規情報の根拠として再利用しません。

②では「今回取得成功した情報源数」「今回の記事確認数」「保存済み記事数」「失敗した情報源の最終成功時刻」「HTTP再試行と復旧数」「再取得可能時刻」を区別します。取得に失敗した情報源を成功数へ加算せず、保存済み67記事を今回67記事取得したとは表示しません。最終成功時刻はこの改善の導入後から記録します。

## 動作上の制限

全BOXの網羅は保証しません。年が不明な期間は判定せず、年省略時は商品仕様の発売年を使用します。このため古い商品の翌年以降の再販は、記事側に年の明記がないと取りこぼすことがあります。

Amazonのアクセス制限・HTML変更で在庫確認できない場合があります。ポケセンの在庫の直接取得は未対応で、現状は取得可能な抽選期間・明示的な再販期間が対象です。日次確認の間に終了する在庫や抽選は見逃します。まとめサイトの誤情報・更新遅延にも影響されます。

## GitHub設定

Repository Secretsを次の2つに分けます。コード・ログ・状態ファイルにはWebhook URLを入れません。

| Secret | 送信内容 |
| --- | --- |
| `DISCORD_WEBHOOK_URL`（①） | 新規抽選・再販・在庫復活・トレトクPSAオリパの販売告知 |
| `DISCORD_HEALTH_WEBHOOK_URL`（②） | 日次ヘルスチェック、およびwatchdogの障害・自動復旧・復旧通知 |

`GITHUB_TOKEN` はActionsが自動提供します。

Actions → **Pokeca daily check** → **Run workflow** から手動実行できます。`Discord接続テストのみ` をオンにすると接続テスト1通だけ送信します。通常実行はオフです。

状態は `monitor-state` ブランチの `state.json` に保存。公開情報の抽出結果・観測状態のみを保存します。Discordの受信確認後に通知済みとして記録するため、送信失敗は次回再試行します。受信後の状態保存に失敗すると同じ通知が重複する可能性はあります。

スケジュールは `0 0 * * *`（UTC）で、日本時間09:00です。GitHub側の混雑で遅延・実行欠落する場合があります。Publicリポジトリの定期実行は活動がないと停止される場合もあるため、Actions画面で稼働状況を確認してください。

## 日次ヘルスチェック（②）

毎日の通常チェックが終わったら、新規情報がない日も②へ実行結果を送ります。予定は毎朝09:00 JSTで、実際の報告はGitHub Actionsの処理完了後です。スケジュールの遅延によって配信時刻も遅れます。

- 正常終了／確認できた範囲では新規情報なし、または新規情報の件数を表示します。
- 本日①へ送信確認済みの件数、今回取得成功した情報源・記事件数と保存済み記事件数、Amazon在庫の判定不能件数と実行ログへのリンクを載せます。判定不能がある場合は「在庫判定に一部制限」と明記します。
- 取得エラー、テスト失敗、監視処理の中断、今回のレポート欠落は「要確認」です。成功した古いレポートで「更新なし」と判断しません。
- `health.py`は監視コードをimportせず、監視ステップが失敗しても実行します。①への送信途中で失敗した場合も、受信確認できた件数を報告します。
- 日本時間の日付ごとに通知済み結果を`health-state`ブランチへ保存。同じ日の再実行は同内容を重複送信せず、障害・復旧・追加送信があれば報告します。状態保存前にDiscord受信確認を待つため、受信後の状態保存失敗では重複する可能性があります。
- 接続テストだけの実行は日次ヘルスチェックに含めません。②の送信失敗もワークフロー失敗となり、watchdogの再試行対象です。②の未設定時に①へ代替送信しません。
- ランナー起動失敗・ジョブ全体のタイムアウト等で報告処理まで動けない場合はwatchdogが補います。GitHub Actions全体の停止中は日次報告もwatchdogも実行できません。

## ローカル検証

Python標準ライブラリのみ使用します。

```sh
python -m unittest discover -v
python monitor.py --dry-run
```

dry-runはDiscord送信・状態保存をしません。結果は `report.json`（Git対象外）に出力します。実際の状態遷移を試すテストは `test_events.py`、トレトクの告知判定は `test_toretoku.py` にあります。

## Watchdogと自動復旧

`Pokeca watchdog` が日次処理の完了時と毎時17分・47分に動作します。

- 日次処理の失敗・タイムアウトを検出すると自動rerun。1障害につき最大2回、再試行間隔は30分以上です。情報源が指定する再取得時刻より前には再実行しません。古いコードで失敗している場合は最新mainを新規実行します。
- 毎朝9時の予定から2時間を過ぎても通常チェックを確認できない場合、1回だけ補完実行を起動します。その実行が失敗した場合も最大2回まで再試行します。
- 実行中の処理は重複起動しません。1時間を超える待機・実行、取消・承認待ち、無効化されたワークフローは要確認通知とします。
- 自動復旧の開始、再試行上限到達、復旧をDiscord②へ通知します。同じ障害・同じ段階では繰り返し送信せず、watchdogの正常確認は無通知です（日次報告は別途②へ送信）。
- 接続テストは日次チェックの成功扱いにしません。通常チェックの表示名は `Pokeca daily monitor`、接続テストは `Discord connection test` です。
- 再試行回数は独立した `watchdog-state` ブランチの `watchdog.json` に保存します。API呼び出しの前に回数を保存し、応答不明時も連続rerunを防ぎます。
- watchdogは監視プログラムをimportせず独立して動きます。`workflow_run` では信頼済みの既定ブランチだけを実行し、forkやPRのコードは読み込みません。

Actions → **Pokeca watchdog** → **Run workflow** のテスト項目をオンにすると、直近の通常チェックを実際にrerunして権限を検証します。実障害の再試行枠は消費しません。30分以内の重複テストは停止します。

watchdog自身もGitHub Actions上で動くため、GitHub Actions全体が停止した場合はその間の検知・復旧を実行できません。Discord自体の障害も同じWebhookでは通知できません。これらを監視するには別サービス上の外部監視が必要です。

仕様: [GitHub workflow_run / schedule](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)、[Workflow runs REST API](https://docs.github.com/en/rest/actions/workflow-runs)。
