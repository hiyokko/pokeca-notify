# ポケカ通知

毎日09:00（日本時間）に、**ポケモンセンターオンラインとAmazon.co.jp販売分**のBOX・BOX入りセットについて、**新しい抽選開始と再販・在庫復活**をDiscordへ通知するGitHub Actionsです。記事の更新自体は通知しません。

## 対象と情報源

既存・新規の拡張パックBOX、ルリナセット・イーブイズセットなどBOXを含むセットを発見対象にします。バラパック、BOXを含まないセット、デッキ、オリパ、サプライ、他店の販売を除外します。商品仕様から判断できない商品は通知しません。

| 情報源 | 用途 |
| --- | --- |
| [ポケゲトちゃんねる](https://pokemon-infomation.com/) | 再販・抽選カテゴリ全記事から商品仕様と対象2店舗の受付期間を抽出。古い記事の変更も確認 |
| [ポケカ抽選ボード](https://chusen-board.com/) | Amazon招待受付中一覧と商品URL。別ソースでポケカBOXと確認した商品のみ採用 |
| [Mirar](https://otoku-mirar.com/amazon-pokemon-card-request-sell) | ポケカBOXのAmazon招待受付中・終了一覧 |
| [カード抽選まとめ](https://cardchusen.com/) | ポケカかつ対象店舗の商品URLを発見。掲載だけでは抽選開始と判定しない |
| Amazon商品ページ | 販売元Amazon.co.jp・購入ボタン・在庫表示が確認できた場合の在庫判定 |

## 通知ルール

- 抽選: 明確な受付期間が開始したとき、終了後に次の抽選回が始まったとき、または既存の複数ソースで新たに受付中と確認できたとき。
- 再販: 明示された再販期間の開始、または確認済みの販売不可→購入可能への変化。
- 期限切れ・受付開始前・記事の日時更新・価格修正・期限延長・当選発表・当選者の購入期間は通知しません。
- 受付開始前の期間を保存し、記事が変わらなくても受付開始時刻を過ぎた日次実行で判定します。
- 商品名・店舗・販売種別で統合。同じ購入機会が複数サイトに載っても1件にまとめます。
- 初回と新ソース追加時は既存情報を基準として保存し、過去の抽選を一斉送信しません。
- 不明や取得失敗を「在庫なし／受付終了」に変換しません。変化がない日は通知しません。
- 情報サイトを根拠にした通知は情報元を明記します。公式確認済みとは表示しません。

## 動作上の制限

全BOXの網羅は保証しません。年が不明な期間は判定せず、年省略時は商品仕様の発売年を使用します。このため古い商品の翌年以降の再販は、記事側に年の明記がないと取りこぼすことがあります。

Amazonのアクセス制限・HTML変更で在庫確認できない場合があります。ポケセンの在庫の直接取得は未対応で、現状は取得可能な抽選期間・明示的な再販期間が対象です。日次確認の間に終了する在庫や抽選は見逃します。まとめサイトの誤情報・更新遅延にも影響されます。

## GitHub設定

Repository Secret `DISCORD_WEBHOOK_URL` に通知先Webhookを登録します。コード・ログ・状態ファイルには入れません。`GITHUB_TOKEN` はActionsが自動提供します。

Actions → **Pokeca daily check** → **Run workflow** から手動実行できます。`Discord接続テストのみ` をオンにすると接続テスト1通だけ送信します。通常実行はオフです。

状態は `monitor-state` ブランチの `state.json` に保存。公開情報の抽出結果・観測状態のみを保存します。Discordの受信確認後に通知済みとして記録するため、送信失敗は次回再試行します。受信後の状態保存に失敗すると同じ通知が重複する可能性はあります。

スケジュールは `0 0 * * *`（UTC）で、日本時間09:00です。GitHub側の混雑で遅延・実行欠落する場合があります。Publicリポジトリの定期実行は活動がないと停止される場合もあるため、Actions画面で稼働状況を確認してください。

## ローカル検証

Python標準ライブラリのみ使用します。

```sh
python -m unittest discover -v
python monitor.py --dry-run
```

dry-runはDiscord送信・状態保存をしません。結果は `report.json`（Git対象外）に出力します。実際の状態遷移を試すテストは `test_events.py` にあります。

## Watchdogと自動復旧

`Pokeca watchdog` が日次処理の完了時と毎時17分・47分に動作します。

- 日次処理の失敗・タイムアウトを検出すると自動rerun。1障害につき最大2回、再試行間隔は30分以上です。古いコードで失敗している場合は最新mainを新規実行します。
- 毎朝9時の予定から2時間を過ぎても通常チェックを確認できない場合、1回だけ補完実行を起動します。その実行が失敗した場合も最大2回まで再試行します。
- 実行中の処理は重複起動しません。1時間を超える待機・実行、取消・承認待ち、無効化されたワークフローは要確認通知とします。
- 自動復旧の開始、再試行上限到達、復旧をDiscordへ通知します。同じ障害・同じ段階では繰り返し送信せず、正常時は無通知です。
- 接続テストは日次チェックの成功扱いにしません。通常チェックの表示名は `Pokeca daily monitor`、接続テストは `Discord connection test` です。
- 再試行回数は独立した `watchdog-state` ブランチの `watchdog.json` に保存します。API呼び出しの前に回数を保存し、応答不明時も連続rerunを防ぎます。
- watchdogは監視プログラムをimportせず独立して動きます。`workflow_run` では信頼済みの既定ブランチだけを実行し、forkやPRのコードは読み込みません。

Actions → **Pokeca watchdog** → **Run workflow** のテスト項目をオンにすると、直近の通常チェックを実際にrerunして権限を検証します。実障害の再試行枠は消費しません。30分以内の重複テストは停止します。

watchdog自身もGitHub Actions上で動くため、GitHub Actions全体が停止した場合はその間の検知・復旧を実行できません。Discord自体の障害も同じWebhookでは通知できません。これらを監視するには別サービス上の外部監視が必要です。

仕様: [GitHub workflow_run / schedule](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)、[Workflow runs REST API](https://docs.github.com/en/rest/actions/workflow-runs)。
